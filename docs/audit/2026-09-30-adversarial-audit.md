## Executive summary

NetSecOps is, on the whole, a soundly-engineered read-only assessment platform whose safety-critical layers were clearly designed with the right instincts: a closed allow-list plus three-layer read-only guard, a deliberate "undecidable" third axis in path analysis, an address-resolution path that refuses rather than returning an empty set, a redaction layer for provenance excerpts, and honesty notes for incomplete coverage. Most confirmed defects are not the absence of these controls but the failure to replicate an already-established guard onto a sibling code path, or an edge case the test fixtures never model (fixtures repeatedly encode the happy case: id==display_name, `inactive:` instead of `deactivate`, null instead of "Original", ISO dates only). That is a reassuring shape — it means the architecture is correct and the work is mostly closing known-pattern gaps rather than rebuilding.

That said, the audit surfaced two genuine CRITICALs and a substantial cluster of HIGHs that undermine the product's central promises. Both criticals live in the PAN-OS/HTTP adapter: (1) the read-only guard's PAN-OS `GET /api/` rule carries no read-only predicate, so a mutating XML-API call (`type=config&action=set`, `type=commit`, `op <request>`) passes the guard that the identical POST is refused by — a direct breach of the READ-ONLY GUARANTEE (SRS §8); and (2) when PAN-OS auth uses username+password, the cleartext admin password is interpolated into the keygen URL, written unredacted into the hash-chained audit log's `command_text`, and served verbatim by `GET /api/v1/audit-log` to any AUDIT_READ holder — a permanent, API-exposed device-credential leak. These two alone warrant immediate remediation.

The dominant HIGH theme is the false-green: unverified, unresolvable, capped, or absent input rendered as a confident clean/blocked/PASS across the firewall model, checks engine, segmentation matrix, parsers, and AAA correlation. Individually medium-to-high; collectively they are the most important finding of the audit because they erode trust in exactly the segmentation and compliance verdicts the product exists to produce. The platform is not unsound, but these gaps must be closed before its verdicts can be relied on for a compliance boundary.

## Cross-cutting themes

- FALSE-GREEN UNDER INCOMPLETE INPUT is the single largest pattern (invariant 2). Empty/unresolvable service objects and groups resolve to a confident non-match; capped segmentation cells report UPHELD over prefix pairs never walked; NCM checks with empty:/count_lte: assertions PASS on absent JMESPath data; certificate-expiry checks PASS when every date is unparseable; dropped Junos default/global policies make a permit look like an implicit deny. Repeatedly the address-resolution path has a guard (model.py:483-489) that the sibling paths simply do not copy.
- PAN-OS / HTTP CREDENTIAL PLANE is the weakest adapter surface and the source of both criticals plus a high: no read-only predicate on the PAN-OS GET rule (write-over-GET), the admin password placed in the keygen URL and persisted/served unredacted, and the TLS certificate pin checked only AFTER the credential-bearing request is already on the wire.
- PARSER FIDELITY GAPS that silently corrupt topology/policy state: Junos (global/default policies dropped, `deactivate` ignored, AAA `$9$` secret unredacted), Arista (interface+gateway route drops the gateway), NSX (mixed static+dynamic group mistyped, catalogue keyed by display_name while rules reference id), cloud (Azure regional service tags and AWS cross-account SG refs mistyped as fixable collection gaps). Each is an edge the shipped fixtures do not exercise.
- SCOPE / MULTI-TENANCY ENFORCEMENT IS APPLIED UNEVENLY in the reporting service: the exceptions register omits both caller-scope and org filters that every sibling template enforces; the executive-summary device total is unscoped while its numerator is scoped; _require_group and _active_findings omit org. Many are latent today because org_id is hardcoded to 1, but they are landmines the moment multi-tenancy is switched on (invariants 6/7).
- 'UNVERIFIED / INCOMPLETE PRESENTED AS COMPLETE' honesty gaps beyond the firewall engine: coverage counts mixing scoped and unscoped populations, the discovery matrix silently dropping IPv6 and degenerate zones with no limitation, AAA correlation emitting confident HIGH findings over never-collected devices, and mid-run ICMP degradation lost for non-responders. The product's stated honesty discipline exists but is not applied consistently (invariant 4).
- TEST FIXTURES MODEL THE HAPPY PATH — a recurring root cause. The exact failing input is untested in almost every parser finding, which is why these shipped: masking fixtures use id==display_name (NSX), synthetic `inactive: set` instead of real `deactivate` (Junos), null instead of the built-in 'Original' object (Check Point), ISO-only dates (certificates), and POST-only write-refusal tests (PAN-OS read-only guard).
- ENGINE/PLUMBING COMPLETENESS: code that exists but is never invoked. JobType.RETENTION has an executor but no creator, so artifact retention silently never runs and the unauthenticated SSO-state table grows without bound; migrations omit indexes the ORM declares (build-failing drift); the 2026-09-29 query-string read-only fix is inert because no GET rule carries a predicate. Wiring, not logic, is the failure.

## Prioritised fixes (from synthesis)

### 1. [CRITICAL] PAN-OS GET rule has no read-only predicate — config writes pass the guard over GET
`backend/netsecops/adapters/policies.py:409`

**Why it matters:** Directly breaches the READ-ONLY GUARANTEE (invariant 1 / SRS §8), the product's defining promise. The PANOS HttpRule('GET','/api/') omits body_predicate, so in ReadOnlyGuard.check_request the predicate guard at readonly.py:422 is skipped and GET /api/?type=config&action=set, type=commit, and op <request> are returned PERMITTED — while the identical POST is refused by its panos_read_only predicate. PAN-OS is documented as fully functional over GET (action=set/delete, commit). The 2026-09-29 query-string fix is inert because no GET rule carries a predicate. Empirically reproduced: mutating GETs PERMITTED, matching POST REFUSED. It is the read-only backstop itself failing, independent of caller carefulness or device-returned values spliced into requests.

**Fix:** Attach body_predicate='panos_read_only' (extended to read query parameters) to the PAN-OS GET /api/ rule, and/or make ReadOnlyGuard reject any GET whose matched rule lacks a predicate for a vendor known to mutate over GET. Add tests asserting GET ?type=config&action=set / type=commit / type=op are REFUSED.

### 2. [CRITICAL] PAN-OS keygen admin password written unredacted into the hash-chained audit log and served by GET /api/v1/audit-log
`backend/netsecops/services/audit.py:90`

**Why it matters:** Violates invariant 8 (device credentials must never reach a log line or API response unredacted) and is aggravated by permanence. On username+password PAN-OS/Panorama auth, auth_exchange (http_transport.py:333) puts the cleartext password in the keygen URL; session.py records command=f'{method} {path}'; AuditService.record scrubs details but stores command_text RAW (audit.py:89-90); command_text is folded into the tamper-evident hash chain (cannot be deleted without breaking verification) and returned verbatim by the AUDIT_READ-gated list endpoint. PAN-OS is uniquely exposed because Check Point/FortiManager carry the password in the JSON body, which is never recorded. A privileged firewall admin credential is leaked cross-scope and permanently.

**Fix:** Do not place the password in the URL — use a supported header/body form and prefer the pre-issued api_key path; and apply scrub_secrets to command_text in AuditService.record (not only to details). Consider rotating/purging affected chains after the fix.

### 3. [HIGH] Junos global and default policies silently dropped — segmentation reports a false 'blocked' when traffic is actually permitted
`backend/netsecops/parsers/juniper/junos.py:571`

**Why it matters:** Dangerous-direction false-green (invariants 2/3) in the product's core segmentation verdict, on the profile's DEFAULT collection path (`show configuration | display set`). _policies accepts only statements beginning with `from-zone`, so `set security policies default-policy permit-all` and `global policy ... then permit` fall through to raw_unparsed (verified: security_rules==[]). The path walk then applies its hardcoded implicit-deny and reports inter-zone traffic BLOCKED/isolated for a device that in fact permits it. Conditional on a permissive default/global policy being configured (so HIGH not CRITICAL), but it degrades an entire device's rulebase to invisible.

**Fix:** Handle `security policies global policy ...` and `default-policy ...` in _policies; represent a permissive default as a catch-all SecurityRule, or add a firewall-model default_action the walk consumes. Add a fixture using real `deactivate`/`default-policy permit-all` lines.

### 4. [HIGH] SSO auto-links an IdP subject to an existing account by unverified email — account takeover
`backend/netsecops/services/sso.py:337`

**Why it matters:** Auth bypass. verify_id_token (oidc.py:382) never checks email_verified (the claim appears nowhere in the backend), and _resolve_user links an attacker's subject to any never-federated account matched purely by case-insensitive email (line 359), then issues that account's session — including a non-MFA Super Admin. Contradicts the module's own stated principle. Contingent on the deployment's IdP permitting user-settable/unverified email (consumer Google, multi-tenant Entra, self-service directories), hence high rather than critical.

**Fix:** Require email_verified==true before the email-link branch; better, disable auto-link-by-email for admin-provisioned accounts and require explicit admin linking or a verified-email confirmation step. Do not set external_idp_subject before the MFA gate.

### 5. [HIGH] DENIED segmentation cell reports UPHELD over prefix pairs never walked (cap-induced false-green)
`backend/netsecops/services/segmentation.py:109`

**Why it matters:** Compliance-visible false-green (invariant 2), contradicting the module's own docstring that a DENIED intent must be checked over the whole zone, not a sample. _prefix_pairs hard-slices the src-outer/dst-inner cartesian product to MAX_PREFIX_PAIRS=16, dropping tail source prefixes entirely; _evaluate_cell derives status only from the walked subset and, with no 'partial' enum state, sets UPHELD and increments matrix.upheld even though an unwalked pair may permit DENIED traffic. Truncation is recorded only as a soft advisory string.

**Fix:** When total > len(pairs) for a DENIED expectation, degrade the cell to UNVERIFIED (add a partial/capped CellStatus) and exclude it from matrix.upheld; surface the cap as a status, not just a limitation string.

### 6. [HIGH] Service object/group resolving to an empty ServiceSet is treated as a confident non-match, not unresolved
`backend/netsecops/firewall/model.py:626`

**Why it matters:** False-green (invariant 2) in the core connectivity engine. A service object whose value is non-empty but unparseable (e.g. FortiOS 'proto-47', named ports like 'https') returns ServiceSet({}) instead of None, so resolve_services never records it in unresolved; likewise a service group whose members are all unresolvable (model.py:564) returns an empty ServiceSet. In first_match this is a DEFINITE service miss, so a permit rule is silently skipped and a query returns implicit-deny as a confident 'blocked'. The address path deliberately guards this exact case and adds to unresolved; the service paths do not.

**Fix:** In _service_from_object return None (and add to unresolved) when a non-empty value parses to an empty port set; in the service-group branch add the `if members and not by_protocol` guard mirroring the address-group guard at model.py:483-489.

### 7. [HIGH] KEV-matched medium/low findings are never notified because severity is filtered before KEV promotion
`backend/netsecops/integrations/triggers.py:181`

**Why it matters:** Correctness defect that silently defeats the 'being exploited right now' alert for exactly the low-CVSS-but-in-KEV class it exists to catch. scan() fetches findings with Finding.severity.in_(('critical','high')), and the KEV_MATCHED promotion (the sole producer, line 202) iterates only those rows. Vuln severity is derived purely from CVSS bands, so a KEV CVE with CVSS < 7.0 is stored medium/low, excluded, and never notified — contradicting the module docstring, wants(), and an existing test asserting a LOW KEV event is deliverable.

**Fix:** Compute KEV membership independently of the severity pre-filter — OR the KEV condition into the query (severity.in_(...) OR cve_id IN kev), or run the KEV lookup over all new findings and promote before filtering.

### 8. [HIGH] JobType.RETENTION has an executor but no creator — artifact retention never runs and the SSO-state table grows unbounded
`backend/netsecops/workers/runner.py:163`

**Why it matters:** A configured compliance control (FR-ADM-01) is a silent no-op, and an unauthenticated resource-exhaustion DoS exists. Nothing creates a RETENTION job: JobService has no create_retention, the generic create() rejects the empty scope a device-less retention job needs, and ScheduleService._create_job has no RETENTION branch (falls through to a ValidationProblem caught as 'skipped' every tick). purge_artifacts and purge_expired_states each have exactly one caller — this dead branch — so evidence is kept past its stated retention window and rows created by the unauthenticated /auth/sso/start endpoint are never swept.

**Fix:** Add create_retention (device-less, bypassing the empty-scope guard like create_notify) plus a RETENTION branch in ScheduleService._create_job, and seed a default nightly retention schedule; add a test that a retention job is actually created and dispatched.

### 9. [HIGH] EOL lifecycle matching ignores product, so one vendor's release cycle shadows another's and clears a real end-of-support finding
`backend/netsecops/services/vuln_assessment.py:414`

**Why it matters:** False-green (invariant 2) that auto-closes a genuine finding. _eol_records filters only on org_id and vendor; _best_cycle matches purely on the parsed release tuple and never consults record.product. For lockstep-versioned products (FortiOS 7.0 vs FortiAnalyzer 7.0) both rows tie and the first DB row wins arbitrarily; if the supported sibling wins, the device is marked SUPPORTED and its real END_OF_SUPPORT finding is resolved via eol_fingerprint (which is keyed on cycle string alone). Product is required at ingest and stored on every row but discarded at match time.

**Fix:** Match EOL records on product as well as version (filter _eol_records by device product or compare record.product in _best_cycle), and include product in eol_fingerprint.

### 10. [HIGH] NCM checks with empty:/count_lte: assertions return PASS on absent (None) data
`backend/netsecops/checks/engine.py:483`

**Why it matters:** False-green (invariant 2): a confident green PASS for security posture derived from data that was never read. engine.py:483 excludes empty/count_lte/count_gte from the None->_missing_outcome guard, and _as_sequence(None) returns [], so empty:true / count_lte pass on missing input. ### 11. [HIGH] certificates_expiring_30/90 drop certs with non-ISO/missing expiry dates and report PASS
`backend/netsecops/checks/python.py:501`

**Why it matters:** False-green (invariant 2) on a high-severity availability check. _certificate_expiry parses only via datetime.fromisoformat and does `except ValueError: continue`, silently dropping real vendor formats (PAN-OS '2027/01/01 00:00:00', Cisco ISE Java Date.toString, FortiAuthenticator epoch). If every date is unreadable, expiring stays empty and the check returns PASS 'No certificate expires within N days' — even for a cert that expired last week. The correct sibling certificate_expiry (uses parse_expiry, returns NOT_EVALUATED) is referenced by no shipped YAML.

**Fix:** Replace fromisoformat with ncm.certificates.parse_expiry (handles epoch/vendor formats) and return NOT_EVALUATED when any date is unreadable; repoint the 30/90 YAMLs at the safe certificate_expiry implementation.

### 12. [HIGH] Exceptions-register report ignores caller scope and org — cross-scope/cross-tenant leak in a frozen, downloadable artefact
`backend/netsecops/services/reporting.py:719`

**Why it matters:** Object-level visibility bypass (invariant 7) and cross-tenant leak (invariant 6). Unlike every sibling template, _exceptions_register runs select(FindingException) with no scope filter and no org_id filter; the accepted `scope` parameter is never used. A group-scoped auditor receives a hash-signed, e-mailable document listing every FindingException in the DB — device_id, check_id, free-text justification, approver — for devices outside their scope and (in multi-org) other tenants. The artefact keeps disclosing after scope is corrected.

**Fix:** Add the visible-device intersection (as _assert_visible / _group_device_ids do) AND FindingException.org_id == self.org_id to the query, matching the sibling templates.

### 13. [HIGH] Never-collected device fabricated into a HIGH 'local-only administrative access' finding from absent data
`backend/netsecops/services/aaa_correlation.py:319`

**Why it matters:** Fabricated precision / false verdict on absent data (invariants 4/2). For a device in inventory but never collected (snapshot=None) while >=1 AAA server was collected, correlate() counts it as devices_not_evaluated yet still appends it as UnregisteredDevice(configured_for_aaa=False), which aaa_assessment renders as a HIGH finding asserting 'Its configuration names no AAA server either, so administrative access here is local-only...' — a specific claim about a configuration that was never read. The same device is simultaneously 'cannot answer' and 'confirmed local-only, HIGH' — a self-contradiction.

**Fix:** Add `if snapshot is None or aaa is None: continue` before the unregistered append; distinguish 'config read, names no server' from 'config never read' so the HIGH local-only text is only emitted for the former.

### 14. [HIGH] HTTP transport verifies/pins the TLS certificate only after the request completes — credential sent to an unauthenticated peer
`backend/netsecops/adapters/http_transport.py:210`

**Why it matters:** Credential-disclosure weakness (invariant 8) that defeats the FR-COL-10 pin for the one request that matters. With verify_device_tls defaulting False, connect() builds a CERT_NONE client and does no pin check; _check_certificate runs only AFTER self._client.request() returns. The first request is the credential-bearing login (PAN-OS password in URL, Check Point/FortiManager password in body). An on-path attacker presenting any cert receives the credential before the post-response pin mismatch fires. SSHTransport, by contrast, verifies the host key in connect() before sending.

**Fix:** Verify the pinned fingerprint before any credential-bearing request — perform a handshake/probe in connect() and compare the pin there (as SSHTransport does), aborting before the login is transmitted.

### 15. [HIGH] Topology cache fingerprint keys on Snapshot.created_at, so an in-place NCM refresh serves a stale graph
`backend/netsecops/services/topology.py:202`

**Why it matters:** Cache-correctness violation (invariant 5) that can produce a stale path/matrix verdict (invariants 2/3). The fingerprint uses max(Snapshot.created_at) (server_default only, no onupdate), while Device/DrSet use updated_at. A config-identical re-collection whose parsed NCM changed (parser upgrade, reconverged routes) updates the snapshot in place — moving updated_at but not created_at and inserting no new row — so the fingerprint never moves and GRAPH_CACHE serves the pre-refresh graph. Verifiers note the realistic direction is often conservative (stale UNKNOWN) and self-heals on the next collection, but it is a genuine TTL-less staleness defect.

**Fix:** Include max(Snapshot.updated_at) (or the normalized_hash) in the fingerprint so an in-place NCM refresh moves it; alternatively invalidate GRAPH_CACHE on any snapshot write.
